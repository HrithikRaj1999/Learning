Story 1: Cleaning Up Hidden Junk in the Database

Situation: At RiffynX, we store lab test data in Amazon DocumentDB. 
Saving new data became painfully slow over a few weeks, even though user traffic stayed exactly the same.
Task: Find out what was slowing down the saves and fix it before scientists lost their experiment work.
Action: I checked the database health first. 
The server ran out of fast memory (RAM) and was reading slowly from the hard drive instead. 
The data itself had not grown, but the indexes (the search shortcuts) were huge.
 Different teams over the years had created duplicate and useless shortcuts. 
 Every time someone saved a single file, the database had to update dozens of these useless shortcuts one by one.
To fix this without breaking the live app, 
I built an end-to-end script that automatically found the useless indexes,
tested deleting them safely on a backup copy first to make sure no search broke, 
and then safely deleted them from the main database during quiet hours.

Result: We deleted 40% of the index junk. Saving data became fast again, 
the server fit in memory, and AWS costs dropped.
I also set up a rule so engineers cannot add new shortcuts without a clear reason.




Story 2: Fixing Crashes from Giant Website Scans

Situation: At NIIT, we built a tool that checks websites to make sure people with disabilities can use them.
 It worked great on small sites, but big clients tried scanning sites with thousands of pages. 
 These took 5 minutes and generated massive files. 
 Because our web server tried to do all the work while making the user wait on the line, 
 the connection timed out after 60 seconds, and the server ran out of memory and crashed.

Task: Stop the crashes and timeouts without forcing clients to change how they send requests.
Action: I split the job into two parts. When a client asks for a scan, the web server now says "Got it!",
 gives them a tracking ID, and puts the job in a line (queue). Background workers pick up the job and 
 do the heavy scanning quietly behind the scenes. For the huge files, I used data streaming 
 so the computer writes the file piece-by-piece instead of holding the whole giant file in memory at once.

Result: Zero crashes, zero timeout errors, and the total wait time dropped by 45%.
What I'd do differently today: I initially used Redis for the job line, which meant 
I had to write custom code to handle lost jobs if a computer died. Today,
 I would use Amazon SQS instead because it handles retrying failed jobs and tracking progress automatically.
